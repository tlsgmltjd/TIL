# jvm application 배포 직후 지연시간 해결 - JVM Warm Up

jvm 서버 배포 직후 요청들의 응답 지연시간이 오래걸리는 현상이 있다. 이러한 현상의 원인과 해결 방법에 알아보겠다.

## 클래스 로더

자바 언어의 컴파일 과정은 우선 javac 컴파일러가 .java 파일을 중간 언어인 .class 파일, 즉 바이트 코드로 컴파일 한다.

이후 클래스를 사용하는 시점에 jvm의 클래스 로더가 사용되는 클래스를 로딩하여 Runtime Data Area에 적재한다.

클래스 로더는 크게 Loading, Linking, Initialization 과정을 거치며 클래스를 읽고 jvm에 적재한다. 이렇듯 클래스 로더는 상대적으로 무거운 작업에 속한다.

클래스 로더가 배포 직후 지연시간에 영향을 미치는 이유는 위에서 말했듯 클래스 정보를 jvm 내에 적재하는 타이밍은 클래스를 사용하는 시점이다. 이렇게 클래스 로더의 Lazy Loading 한 동작 방식은 최초 클래스 참조 시점에 로딩하기 때문에 메모리에 적재되지 않은 클래스를 참조하는 시간은 오래걸린다.

## JIT 컴파일러

자바는 인터프리터 방식과 컴파일 방식을 둘 다 사용한다.

인터프리터 방식은 빠르게 프로그램을 실행할 수 있지만, 실행 후 코드를 한줄 한줄 읽으며 동작하기 때문에 상대적으로 느리다. 컴파일 방식은 프로그램 실행시 모든 코드를 기계어로 변환하는 컴파일 과정을 거치고 실행하기 때문에 초기 실행이 느리지만, 실행 후 기계어로 변역된 프로그램 코드는 컴퓨터가 빠르게 실행시킬 수 있다. 이러한 인터프리터와 컴파일 방식의 장점을 모두 갖기 위해 자바에서는 두 방식을 혼용해 사용한다. (기본적으로 인터프리터 방식으로 코드를 실행한다.)

또한, 자바는 OS에 종속되지 않는 컴파일 방식을 제공한다. jvm에서 실행 전에 자바 바이트 코드로 중간 단계 컴파일을 진행하고 jvm에서 실행하기 때문에 OS가 달라지더라도 jvm만 같다면 실행할 수 있다.

하지만 자바 바이트 코드는 기계어가 아니기 때문에 jvm에서 이후 인터프리터 방식으로 코드를 실행하면 느리게 실행될 수 밖에 없다.

자바는 이러한 인터프리터 방식의 성능 문제를 해결하기 위해 JIT(Just In Time) 컴파일러를 도입했다. JIT 컴파일러는 런타임 중에 동적으로 바이트 코드를 기계어로 컴파일하여 캐시 저장소에 보관한다. 이후 동일한 코드를 실행할 때 캐시된 코드를 읽게 되어 빠르게 실행할 수 있다.

JIT 컴파일러는 자주 사용된다고 판단되는 특정 부분(핫스팟)을 기계어로 컴파일하여 캐시한다. 내부적으로 애플리케이션을 동적으로 분석하고, 코드 실행 횟수, 메서드 호출 횟수, 루프 반복 등을 기록하는 프로파일링을 진행하여 핫스팟을 찾는다.

### JIT 내부 동작

JIT 컴파일러는 최적화 수준에 따라 적절한 최적화 수준으로 바이크 코드를 컴파일 한다. 이것을 Tiered Compilation이라고 부른다.

### Tiered Compilation

JIT Tiered Compilation은 총 5개의 Level로 나뉘며 Level 0은 인터프리터(기본), Level 1~3은 C1 컴파일러, Level 4는 C2 컴파일러에 의해 수행된다.

- Level 0: 가장 기본적인 실행 단계로, 바이트코드를 인터프리터 방식으로 실행한다.
- Level 1: C1 컴파일러를 통해 빠르게 컴파일 하지만 최적화는 거의 없는 단계다.
- Level 2: C1 컴파일러를 사용하여 약간의 최적화를 적용한다.
- Level 3: C1 컴파일 수준에서 가능한 최적화를 최대로 적용한다.
- Level 4: C2 컴파일러를 통해 가장 고성능 최적화를 적용한다. 컴파일 시간을 오래 걸리지만 실행 성능은 최상이다.

## JVM Warm-up

jvm 서버 배포 직후 요청들의 응답 지연시간이 오래걸리는 이유응 앞서 설명한 두가지가 원인이다. "클래스가 아직 메모리에 적재되지 않은 상황(클래스로더 Lazy-Loading)", "JIT 컴파일러가 아직 코드를 최적화 하지 않아서" 이다.

이러한 문제를 해결하기 위해 JVM을 미리 워밍업하여, 초기 실행시간을 단축할 수 있다.

그럼 애플리케이션 실행 시점에, 자주 호출되는 코드를 충분히 많이 실행해두면 된다. 이러한 작업을 JVM Warm-up이라고 한다.

간단하게 스프링에서는 `ApplicationReadyEvent`를 핸들링하거나 `ApplicationRunner`를 구현하여 JVM Warm-up을 구현할 수 있다.

```java
@Component
public class WarmupRunner implements ApplicationRunner {

    @Override
    public void run(ApplicationArguments args) {
        System.out.println("[Warmup] 시작");

        for (int i = 0; i < 10_000; i++) {
            // warm up target method
        }
        System.out.println("[Warmup] 완료");
    }
}
```

C1 컴파일러의 최적화 실행 임계치는 약 1,500회이고 C2 컴파일러의 최적화 실행 임계치는 약 10,000회 이다. 최적화 목적에 맞춰 코드를 반복 실행하여 Warm-up을 하면 된다.
